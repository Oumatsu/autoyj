# Vehicle Detail Full-Locale Translation Design

## Objective

Make every public vehicle-detail page fully understandable after switching to Chinese or Amharic. Coverage includes the shared interface, all 47 vehicle-specific pages, and all 251 currently stored Trim/version records.

`I18n Locale` remains the translation source of truth. Vehicle and Trim business tables keep their English source data; translations are stored as separate i18n records and connected through the existing bidirectional relation fields.

## Chosen Architecture

The Worker continues returning English source values, plus stable identifiers. The client resolves locale-specific values through the existing `useTranslation()` mechanism. English remains the final fallback if a translation is missing or malformed.

This preserves one translation system for the entire site:

```text
Feishu business tables
  -> Worker English detail payload + stable IDs
  -> translation key helper
  -> useTranslation / t / tArray
  -> Chinese, English, or Amharic detail interface
```

Both runtime translations from `/api/portal/public/translations` and build-time dictionaries generated by `scripts/sync-i18n.mjs` use the same keys. Build-time dictionaries must contain the complete manifest so locale switching never briefly exposes English while live translations are loading.

## Translation Layers and Relation Rules

### 1. Shared interface copy

Key prefix:

```text
productsDetail.ui.*
```

Examples include breadcrumbs, buttons, section headings, gallery controls, business-case copy, batch-profit labels, specification headings, Trim headings, status labels, empty states, source labels, recommendations, and explanatory notes.

Relation fields:

- `Linked Vehicle Model`: empty
- `Linked vehicle_variants`: empty

These strings are shared by every detail page and do not belong to one vehicle record.

### 2. Vehicle-level content

Key prefix:

```text
productsDetail.models.<slug>.*
```

Each record must set:

- `Linked Vehicle Model`: the exact `Vehicle Models` record matched by the final segment of `Product Path`
- `Linked vehicle_variants`: empty

Vehicle-level coverage includes:

- official display name, reusing `catalog.models.<slug>.displayName` where appropriate
- page title and subtitle
- hero description
- why-section description
- charging/supply prose
- model tags and gallery labels when present
- generated feature-card prose that contains model data
- model-level common Trim features
- Trim source summary
- every text-valued specification shown on the page

Pure numbers, currency amounts, URLs, image paths, and locale-neutral units do not receive redundant translation rows. Human-readable words surrounding those values do.

### 3. Trim/version-level content

Key prefix:

```text
productsDetail.variants.<trim-config-id>.*
```

Each record must set both:

- `Linked Vehicle Model`: the model reached through `vehicle_variants.Vehicle Model Pruned`
- `Linked vehicle_variants`: the exact `vehicle_variants` record

Trim-level coverage includes:

- `trimName`
- `batteryChemistry`
- `drivetrainDisplay`
- `baseFeatures`
- `addedFeatures`
- `upgradedFeatures`
- any other human-readable Trim-specific value added to the public payload

The three feature lists are stored in ZH/EN/AM as JSON arrays under one translation key per source field. The existing dynamic translation endpoint and `sync-i18n.mjs` already parse values beginning with `[` as arrays. The client must use `tArray()` or a type-checked equivalent and fall back to the original English array if the stored translation is not an array.

## Stable Identity and Matching

Names are not identifiers. Matching must use existing stable business and relation keys:

- vehicle: slug from `Vehicle Models.Product Path`
- Trim: `vehicle_variants.Trim Config ID`
- vehicle record relation: existing `Vehicle Model Pruned` link
- Trim record relation: the Trim record's `record_id`

The Worker detail response will expose:

```ts
type DetailIdentity = {
  modelId: string;
  slug: string;
};

type TrimIdentity = {
  trimConfigId: string;
};
```

The frontend must not build keys from translated names, Trim display names, array positions, or Trim order.

Before any translation write, the manifest validator must prove:

- 47 unique vehicle slugs
- 47 unique Model IDs
- 251 unique Trim Config IDs
- every Trim links to exactly one Vehicle Model
- every Trim's linked vehicle has the same Model ID
- no generated translation key is duplicated

Any mismatch aborts before creating or updating translation records.

## Frontend Components

### Detail translation key helpers

A focused helper module will own:

- shared-detail keys
- model keys from slug
- variant keys from Trim Config ID
- safe string translation with English fallback
- safe array translation with English-array fallback

The helper must not fetch data or contain UI rendering.

### Vehicle detail renderer

`app/products/_VehicleDetail.tsx` will replace every user-visible hardcoded English string with a shared translation key. Dynamic model fields will be resolved through the model key helper. Each Trim card/table will resolve its own fields through the variant key helper.

The component may continue using raw English values for internal comparisons and styling rules, but only translated values may be rendered to the user.

### Detail page loader

`views/products/[category]/[slug].tsx` keeps the current loading and error flow. The translated loading/error strings remain available immediately from the static locale dictionary.

## Worker/API Changes

`worker/portal.ts` will add `modelId` and `slug` to the detail payload and `trimConfigId` to every `trimComparison.trims[]` entry. No locale parameter is added to the API, and no translated values are written into the vehicle business tables.

Generated English display text remains deterministic so it can be used as the EN translation and fallback. The Worker must not use localized strings for database matching, cache keys, filters, or Trim-ladder calculations.

## Translation Manifest and Database Writer

A dedicated detail-i18n manifest script will:

1. Read all 47 model records and all 251 variant records from live Base data.
2. Validate the model/Trim identity graph before writes.
3. Generate the complete shared, model, and variant translation manifest.
4. Compare it with existing `I18n Locale` records by exact Key.
5. Create missing rows and update only rows owned by the detail manifest.
6. Write relation cells according to the layer rules above.
7. Never delete unrelated translation rows.

Writes are idempotent. Re-running the script updates the same keys and relation cells rather than creating duplicates.

The script defaults to dry-run. A separate explicit write flag is required to mutate Base. Database writes are serialized, with batches no larger than 200 records.

## Translation Quality Rules

### Chinese

- Use official Chinese brand and model names where source-backed.
- Use normal Chinese automotive terminology rather than literal word-for-word translation.
- Keep technical acronyms such as CLTC, WLTP, V2L, AWD, RWD, LFP, NCM, LiDAR, and ADAS.
- Preserve all numbers, ranges, percentages, currency values, placeholders, and units.

### Amharic

- Ordinary interface and automotive meaning must be understandable in Amharic.
- Brand names, official product names, technical acronyms, platform names, and terms without a reliable natural Amharic equivalent may remain English or be transliterated.
- Do not leave complete ordinary English sentences as Amharic values.
- Preserve all numbers, ranges, percentages, currency values, placeholders, and units.

### Structured values

- JSON arrays must remain valid JSON arrays in every locale.
- Array lengths and item order must match the English source field.
- Runtime placeholders such as `{total}`, `{start}`, and `{end}` must remain unchanged.
- No translator may alter record IDs, slugs, Trim Config IDs, URLs, or relation IDs.

## Incremental Execution

Implementation is divided into three independently verified batches while preserving one final full-coverage objective:

1. Shared interface translation and frontend key plumbing.
2. Vehicle-level translation for all 47 models and `Linked Vehicle Model` relations.
3. Trim-level translation for all 251 variants and both relation fields.

A batch is not considered complete until its frontend behavior and Base relations pass. Later batches do not require rewriting or deleting earlier batch records.

## Failure Handling

- Manifest validation failure: no database writes.
- Missing translation: render the exact English source value and report the missing key in tests; never render a raw key.
- Malformed array translation: use the original English array; never call `.map()` on an unchecked value.
- Database write failure: stop on the first failed batch, report the Key and target record IDs, then safely rerun after correction.
- Relation mismatch: do not guess from names; stop and repair the source relationship first.
- Runtime translation endpoint failure: complete static dictionaries keep the selected locale readable.

## Verification and Acceptance

### Automated checks

- Key helper tests for shared, model, and Trim keys.
- Worker payload tests proving every detail response includes model slug/ID and every Trim includes Trim Config ID.
- Manifest tests proving 47 models and 251 variants are covered without duplicate keys.
- Translation quality tests proving Chinese and Amharic values exist and structured arrays remain valid.
- Amharic tests reject ordinary prose identical to English except for an explicit allowlist of brands, official names, acronyms, and units.
- Source scan ensures no user-visible hardcoded English remains in the active detail renderer.
- Component tests cover string and array fallbacks so malformed data cannot create a black screen.

### Database acceptance

- Shared keys have no model or variant relation.
- Every model key links to exactly one correct Vehicle Model and no variant.
- Every variant key links to exactly one correct Vehicle Model and one correct `vehicle_variants` record.
- Reverse relation counts match the generated manifest.
- Existing unrelated translations and the current 94 catalog-model relations remain intact.

### Page acceptance

- Verify Chinese and Amharic rendering for at least one model from each of the three product categories.
- Verify a model with six Trim versions and a model with fewer Trim versions.
- Check hero, gallery, business case, specifications, Trim cards, Trim comparison table, common features, buttons, loading, error, and empty states.
- Switching locale must not briefly expose English copy because the complete static dictionary is bundled.
- English pages remain unchanged except for stable payload identifiers and translation plumbing.

## Scope Boundaries

- This project does not translate the authenticated portal/admin interface.
- It does not rewrite source English business data in `Vehicle Models` or `vehicle_variants`.
- It does not add locale-specific API endpoints or duplicate ZH/AM columns in business tables.
- It does not push or deploy unless separately requested.
